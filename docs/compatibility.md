# Compatibility evidence

Paseo Bot currently targets exactly Paseo **0.13.2**. The installed CLI, daemon, app, client SDK, protocol and plugin SDK were inspected at that version; this is not a claim about earlier versions or future releases. The first release guarantees desktop and compact mobile browsers. Native devices are not guaranteed, as explicitly accepted in specification decision 15.

| Capability | Supported public path in 0.13.2 | Evidence and limit |
| --- | --- | --- |
| Global page, sidebar, themes and compact layout | `@getpaseo/plugin/client`, React Native primitives | Plugin loads on an isolated daemon; browser evidence belongs in the ticket verification record. |
| Background directory workspace | `paseo.workspaces.create({ source: { kind: "directory", path }, background: true, idempotencyKey })` | Real isolated-daemon test creates one owned workspace without Git. |
| Conversation creation and durable identity | Workspace `agents.create`, explicit `agentId`, `idempotencyKey`, labels | Concurrent duplicate request returns one identity; actual timeline read through SDK succeeds. Plugin metadata stores references and request fingerprints, not transcripts. |
| Provider, model, modes and thinking choices | `paseo.providers.waitForReady`, provider/model catalog | Server validates actual available choices before creating resources. A thinking choice is required when the model offers choices. |
| Streaming and saved history | Agent `timeline.subscribe`, `timeline.refetch` | Fixture provider emits a streaming answer through a real daemon. The SDK explicitly requires history refetch after `subscription_restored` and replacement events; the page subscribes before its initial fetch and refetches on events. |
| Tool state/results | Public `AgentTimelineItem` tool-call union | Real isolated-daemon tests and actual Codex tool/result acceptance; see [issue #3](verification/issue-3.md). |
| Permission and provider questions | `pendingPermissions`, `respondToPermission({ requestId, response })` | The public request kind includes `question`; `updatedInput` supports provider-defined answers. Installed Codex maps known questions to header-keyed `updatedInput.answers`. Actual permission and async-question chains plus multi-select/custom-answer regression are recorded in [issue #3](verification/issue-3.md). |
| Stop | Public CLI `paseo agent stop <exact-id> --home <selected-daemon-home> --json` | High-level Agent handle has no stop method. Exact owned session and selected home are required. The plugin verifies status and activeTurn after CLI success; real failure/Stop acceptance is recorded in [issue #3](verification/issue-3.md). |
| Rename | Public CLI `paseo agent update <exact-id> --name <title> --home <selected-daemon-home> --json` | High-level Agent handle has no rename method. Fresh title confirmation and real history/rename acceptance are recorded in [issue #4](verification/issue-4.md). |
| Archive and rebuild | Public Agent `archive`, workspace lifecycle hook, explicit `workspaces.create({workspaceId, ...})` | Isolated tests confirm Stop before archive, failed cancellation blocks archive, concurrent rebuild creates one new background identity, old history/files remain. See [issue #5 evidence](verification/issue-5.md). |
| Durable archived-workspace inspection | Public Node driver `inspectWorkspaceRecovery`, public selected-home daemon-control authentication | Packaged ordinary ESM helper avoids the 0.13.2 CJS plugin bundler’s `import.meta` limitation. Public selected-home plugin listing supplies the installed helper path. Missing resources differ from proven archive; failures block rebuild. |
| Schedules and delegation | Existing host-provided management MCP tools; public parent labels, Agent/workspace refresh, `navigation.openAgent` / `openWorkspace` | Owned Bot guidance preserves Provider permissions and tool policy; actual parent/same-host navigation passes real-daemon tests. Native `create_workspace` requires explicit `background:false`; canonical `create_agent` provides `notifyOnFinish:true`. Actual Codex MCP queries, existing schedule management, existing recipient/native completion, visible business workspace/child completion, target navigation and compact acceptance passed; see [issue #7](verification/issue-7.md). |
| Delivery identity/reconnect | Explicit creation IDs and `send(text, { messageId })`, public timeline pages and observation events | Lost acknowledgements, pre-dispatch loss, explicit same-ID retry, storage failures and two-device recovery have actual browser evidence in [issue #6](verification/issue-6.md). No atomic reject-if-busy operation exists for a competing external sender. |
| Browser device preferences | Platform-gated `client/web.ts`, standard browser storage | No DOM globals in components, no DOM TypeScript lib, no private host imports. Storage denial is shown to the user. |
| Native durable device state | No public storage path found | Allowed modules omit AsyncStorage; global screens have no persisted tab state. Host settings are shared across devices and do not meet this boundary. Native persistence remains unsupported. |

The plugin's backend resolves files against the selected daemon's inherited `PASEO_HOME`, normally `~/.paseo`. Tests supply an isolated temporary daemon home, generated test password and loopback listener. Deployment `PASEO_*` environment overrides are removed from test child processes; existing Provider authentication and the user's home environment are preserved. Production lifecycle and configuration are untouched.

Public documentation consulted: [plugin reference](https://paseo.sh/docs/plugins/reference), [SDK events](https://paseo.sh/docs/sdk/events). Installed public declaration exports and CLI help were checked rather than assuming the sibling source checkout matches the installed release. Runtime claims are limited to the linked per-ticket acceptance records. Management tools are not injected or enabled by this plugin; daemon/Provider policy remains authoritative. Codex is the actually exercised Provider; other Providers have not been independently accepted. Electron is untested. During a disconnect, the host may unmount the plugin page; saved browser state restores on reconnect/reopen, without a promise of continuous offline editing.
