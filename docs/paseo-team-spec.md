# Paseo Team confirmed specification

状态：已确认产品增量，2026-10-28。本分支实现 #15 与 #16 的完整预设生命周期；最终运行证据以对应验收记录为准。本规格不代表增量已经部署，不授权生产安装、配置修改、发布或标识迁移。

依据：[父需求 #13](https://github.com/hulkzzhou1/paseo-bot/issues/13)（最新确认 updatedAt 为 `2026-10-28T09:34:45Z`）、[#14 调研](https://github.com/hulkzzhou1/paseo-bot/issues/14)及[项目词汇](glossary.md)。回退确认见 [#14 最新记录](https://github.com/hulkzzhou1/paseo-bot/issues/14#issuecomment-6465521269)（`2026-10-28T09:34:48Z`）。[现有 Bot 规格](spec.md)保留为已部署行为及历史决策记录；本稿只规定 Team 首版增量，不宣称这些增量已经部署。

## 问题

现有 Bot 已提供持续对话、项目 Agent 委派与历史，但用户仍可能被要求重复选择技能或确认已有授权，项目调查与阶段成果也未形成一致的协调体验。通用角色规则固定在插件中，用户无法通过现有预设入口统一调整新会话的规则与运行配置。

## 方案与实际增量

Paseo Team 由一个持续负责目标推进的 Coordinator，按任务需要组织可跨项目的 Project Agents。Role 由预设表达，具体 Agent 按任务创建或复用，不固定人数、分工或技能顺序。

每 host 一个 Team 入口，支持多个独立 Goal conversations。共享角色预设与通用规则，各会话目标上下文独立；跨会话通过任务记录和项目文档续接，不混合聊天历史。

| 直接复用现有 Bot | 本次增量 |
| --- | --- |
| 专用工作区、原生会话/草稿/权限交互、历史、父子 Agent 生命周期及通知 | 首次打开时辅助创建专属 Coordinator 预设，并说明 notes 的插件用途 |
| 每 host 单入口和多个独立会话；项目 Agent 承担具体工作 | 新建时采用专属预设指定运行参数，并将规则真实加载一次 |
| 既有状态、身份与不明结果恢复接缝，不复制会话转录 | 以意图、事实和已有授权驱动协调，明确阶段成果和用户反馈的后续处理 |

用户主要通过 Coordinator 对话推进任务。独立总览只在以后出现具体使用缺口时讨论。本分支将入口和页面展示名调整为 Paseo Team。包名、插件安装 ID、已有 workspace/Agent/历史身份保持原样，不做迁移。

## 用户行为

### 首次打开与后续会话

1. 用户首次打开入口，明确选择一个已有系统预设作为运行配置来源。插件复制标准运行字段，为新的专属 ID 填入[通用规则文案](#默认通用规则)，并说明该预设的 notes 会由插件作为 Coordinator 规则加载。
2. 完成辅助创建后进入现有 Bot 工作区；打开入口不创建空 Agent，实际发送仍由原生会话机制处理。后续入口复用已有资源，不重复初始化。
3. 专属预设此后独立编辑，不跟随来源预设同步。用户通过系统 Agent profiles 修改其运行配置和 notes；新会话使用最新内容，旧会话与历史不自动改写或重放。
4. 普通项目 Agent 不接受 Coordinator 规则。其角色和配置按具体派工选择，沿用真实项目工作区与父子生命周期。

这发生在**首次打开**，不是插件安装、启用或一次性 install hook；不得用安装成功宣称预设已经创建。

### 按意图协调

- 能依据已有证据回答时直接回答，不强制建单、派工或走完整技能链。
- 需要项目事实时，依据问题类别、所属项目、已有事项和项目 tracker/forge 约定登记或复用父需求、创建调研子任务，再交 Project Agent 调查。新事项使用新 Agent；同一事项已有相关基础时复用。不能仅凭代码 remote 决定 tracker，工具缺失不暗换平台。
- 有明确调研成果时同步子任务，保留编辑父需求方案草案；只有真实未决取舍才在原协调对话讨论，按需使用适用技能，再记录决定。调查或设计确认不自动授权实施。
- Coordinator 汇总进展、处理反馈并跟进后续动作。已有授权在原范围内复用，不让用户机械重输每个技能命令。普通 Agent 回合结束是通知，只有明确阶段成果才回写业务记录，不把回合完成当验收完成。

平台字段、状态与正式关联操作留给项目约定和平台工具，不写入默认通用规则。

## 关键决定与接口边界

### 预设是新会话的规则和运行配置来源

仅使用现有公开 `config.get/patch`、handler、`agent.create` before hook 与 `systemPrompt`。不改宿主、不新增协议字段或生命周期，不导入内部模块，不直接读写宿主配置文件。

- 唯一明确的专属 profileId 对应 Coordinator 预设；同名预设不能冒认。只投影所需预设数据，不输出、缓存或传给 Agent 其他配置。
- notes 标准语义是适用场景，系统不会自动注入。这里采用用户已接受的**插件显式加载约定**；入口应说明其用途，其他预设保持原语义。notes 会被系统 list_profiles 看到，不存凭据。
- 原生与旧 RPC 共用解析，采用专属预设明确指定的 provider/model/mode/thinking/features，不能让另一份输入配置覆盖它。未指定字段沿用现有系统语义，不硬编码模型或自动升权。
- 现有公开接口不能在原生 UI 自动预选 profileId，复用已有 picker 与入口说明。保留既有 provider/权限配置校验，不静默更换权限。旧 SDK 创建需要有效 provider/model，不能用占位模型等待 hook 修复；模型未指定或不可解析时如实提示所缺配置，不等同于预设删除。
- 将现有 managementPrompt 的通用角色规则作为首次填充及已确认缺失回退的公开默认文案；预设存在时，用户 notes 是活跃规则来源，两条创建路径不再追加另一份完整旧规则。通过 systemPrompt 真正加载一次，保留其他不冲突的合法配置，不能只检查 notes 已保存。
- notes 清空是合法选择，不能回填默认。升级、重载、启用和重启不覆盖预设内容或运行配置；旧会话保留创建时指令。

### 保留编辑与未知结果

复用插件现有状态保存关联和初始化结果，不复制活跃规则或新增状态库。初始化使用稳定 ID、本插件串行操作、写前读取及写后核实，保留其他预设和人工编辑。

公开 patch 替换整个 profiles 列表，没有跨客户端 CAS。上述措施只降低竞争窗口，不能保证另一个客户端在读写间的编辑不被覆盖；用户已接受该限制。结果未知先按稳定 ID 回读，不反复覆盖或盲目重建；本插件队列不是全局事务。

删除预设不自动重建，卸载不主动删除宿主预设。已有会话与历史保留。插件状态被清理或读取失败不能被当成确认删除，也不能假称始终能恢复原关联。

初始化写入前，在原有插件状态内保存稳定 ID、初始化意图和已尝试写入标志。丢失确认时先回读同一 ID：找到就采用当前内容（包括人工编辑），不再写种子。仍找不到且旧写入结果不明时，仅继续核查，不重复提交整个列表。明确的配置权限拒绝与未分派前的字段校验失败允许用户修正后重试；不把它们显示为确认删除。读取/解析失败使用脱敏错误，不回显原始配置或错误中可能携带的内容。

普通升级、禁用再启用、重载、隔离重启及同安装 ID 重装复用关联。新版本默认文案改变也不覆盖现有预设，卸载不主动删除预设、插件自有记录或宿主会话。新记录保留最少的初始化标记，用于发现关联字段丢失；旧记录仍按原身份兼容，不迁移工作区或会话。

状态文件缺失、损坏，或初始化标记与关联不一致时，报告身份未知，需恢复原插件数据。整份自有元数据被清理后，如果公开预设列表仍有插件保留 ID 命名空间的对象，或公开工作区列表仍有专用目录的资源，只把它们当作丢失状态的迹象：报错而不收养、不按名称匹配、不盲造第二套资源。此检测不授予历史所有权。若所有元数据与可观察迹象一并被删除，公开接口无法保证区分首次使用与历史状态被清理，也无法恢复旧关联；不声称具备这种恢复保证。确认保留关联的预设删除与这些未知状态不同，仍按下文正常回退，不要求重新绑定。

### 已确认：专属预设缺失时采用通用规则回退

用户已选择“采用通用规则回退”。成功读取当前预设列表，确认专属预设被删除或目标 ID 不存在后，新会话使用**原生界面的有效运行配置＋插件公开说明的默认通用协调规则**。不自动重建预设、不要求重新绑定、不因缺失该预设阻止新建；旧会话与历史不改写。

旧 RPC 没有原生表单时使用其既有明确输入配置，不从其他客户端偏好猜配置或模型。该回退规则必须公开说明，不恢复用户曾删除的自定义内容，也不额外追加一份旧 managementPrompt。

有预设且 notes 为空仍表示有效用户选择，继续使用空值，不能触发默认回填。网络、权限、配置解析失败、关联身份未知和模型缺省均与确认缺失分开：报告真实状态并沿既有恢复处理，不静默进入删除回退。完全原生、不附加规则的备选未采用，不再作为待选问题。

### 平台协作能力

项目跟踪系统、代码托管和正式关联操作由所属项目的技能与工具承担。Team 只消费实际可用能力，不复制平台逻辑，不猜写入接口，不用正文链接或第三方关系冒充正式关联。外部平台的工程阻塞单独报告，不作为本插件已交付或本票必须修复的能力。

## 不在首版范围

多团队管理、固定团队岗位/人数、固定工作流或技能链、独立团队看板、共享记忆库或聊天历史混合、跨 host 调度；宿主增强、私有模块或配置文件绕行、独立规则编辑页、主机共享提示；包名/安装 ID/已有资源身份迁移及自动重建删除的预设。平台插件的修复由独立项目承担，不在 Team 内重做。

## 默认通用规则

以下公开文案是首次创建预设及确认缺失时的默认值；预设存在后以其 notes 为活跃规则，不另加一份隐藏角色规则。

> 你是 Paseo Bot，负责与用户持续沟通、判断下一步并协调项目 Agent。理解当前意图，结合已有事实与授权推进；能直接回答就回答，需要项目证据时请相关项目 Agent 调查，需要用户取舍时只讨论真正未决的问题，需要执行时沿用已有明确授权。项目 Agent 负责具体项目工作，你负责汇总结果、回应变化并推动下一步。
>
> 遵循所属项目的记录、协作与交付约定；仅在相应动作确有需要时登记和回写，保留已有内容，区分回合结束、阶段成果与验收完成。按任务需要使用适用技能，不强制固定阶段或技能链，不让用户重复已确认的选择和授权。
>
> 区分事实、推断和未知；工具缺失、目标不明或结果未验证时如实说明。调查不自动授权实现，方案确认不自动授权发布。尊重真实权限和操作边界，不读取或暴露私人配置与凭据，不声称未验证的工作已经完成。
